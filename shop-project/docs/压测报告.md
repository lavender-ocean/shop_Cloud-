# 外卖项目压测报告

> 被测系统：sky-take-out 扩展版（Spring Boot 2.7 + MyBatis + Redis + Redisson + RabbitMQ）
> 测试日期：2026-10-13　　压测方式：自研 Node 脚本（`docs/压测/`，零依赖）
> 原始数据：`docs/压测/results/*.json`（每次运行均落盘，可复核）

---

## 一、结论速览

| 场景 | 并发 | 吞吐 | P99 | 错误率 | 关键结论 |
|---|---|---|---|---|---|
| 缓存读取（菜品/分类） | 200 | **6,437 QPS** | 68.7 ms | 0% | 30 秒 19.3 万请求，DB 只被查 **1 次** |
| 缓存击穿（清空后猛打） | 100 | 5,709 QPS | 48.9 ms | 0% | 2.8 万请求 → DB 仅回源 **2 次**，回源比 **14216:1** |
| 秒杀抢购 + 防超卖 | 200 | **3,725 QPS** | 134.6 ms | 0% | 100 件库存 **618 ms 售罄**；成功 **恰好 100** 单，**零超卖** |
| 限流验证 | 20（同一用户） | 5,583 QPS | 8.8 ms | 0% | 5.6 万请求仅 **30 次**放行 = 3 次/秒 × 10 秒，**精确命中配置** |
| 下单主链路 | 50 | **225 QPS** | 300.9 ms | 0% | **瓶颈：数据库连接池默认只有 8 条**（详见 §五） |

**三个最有价值的发现**
1. **秒杀正确性**：200 并发 × 2000 用户池抢 100 件库存 → 订单数恰好 100、Redis 与 DB 库存同时归零、去重用户数 100，**零超卖、最终一致**。
2. **缓存击穿防护有效**：清空缓存后 100 并发猛打，DB 只回源 2 次（每个 key 一次），证明「分段锁 + 双重检查」挡住了缓存击穿。
3. **定位到真实瓶颈**：下单接口 P50(220ms) ≈ 均值(220ms) ≈ P99(301ms) —— 典型的「排队等资源」形态；`Max_used_connections = 10` 说明应用侧只开了 8 条 DB 连接，**Druid 未配置 `max-active`，用的是默认值 8**。

## 二、测试环境与口径（数字可不可信，全看这一节）

### 2.1 环境
| 项 | 值 |
|---|---|
| CPU / 内存 | i7-13700H（14 核 20 线程）/ 16 GB |
| 部署形态 | **单机 all-in-one**：应用 + MySQL + Redis + RabbitMQ + 压测器都在同一台机器 |
| 应用配置 | Druid `max-active` 未配置（默认 8）；Tomcat `max-threads` 未配置（默认 200）；Redis 单实例；RabbitMQ 单节点 |
| 压测工具 | 自研 Node 脚本（`http` 内置模块 + keep-alive 连接池），支持分位数统计与业务码分类 |
| 虚拟用户 | 离线签发 HS256 JWT，id 从 9001 起，与真实用户隔离 |

### 2.2 压测模型
- **闭模型（closed-loop）**：启动 N 个虚拟用户，每个用户「发请求 → 等响应 → 再发下一个」，实际压力 = N 个并发在途请求（贴近真实用户行为）。
- **warmup**：先跑 3 秒不计入指标（跳过 JIT、连接池建连、缓存预热），避免把冷启动开销算进来。
- **口径**：
  - `QPS = 完成请求数 / 测量窗口`
  - 延迟分位数取排序后的 nearest-rank 值，**不用平均值代替**（长尾会被平均掩盖）
  - 「失败」按业务语义判定，不只看 HTTP 200（本项目业务错误也返回 200，例如秒杀售罄 `code=0`）

### 2.3 ⚠️ 局限（写简历/答辩时必须主动说明）
1. **单机部署 → 绝对 QPS 不代表应用容量上限**。压测器与 JVM、MySQL、Redis 抢同一块 CPU：压测读取场景时，单进程压测器在 c=20 已达 6.5k QPS，加到 c=200 仍是 6.4k（只有 P99 恶化）；换 3 进程才提到 7.6k。**这是压测机先饱和，不是应用先饱和。**
2. **未测分布式**：项目支持多实例（Redisson 锁、MQ 竞争消费），但本次只测单实例。
3. **未做长稳测试**（连续 1 小时以上）与 **MQ 积压场景**。

> 建议表述：把结果写成「单机实测」并附限定条件，而不是「系统支持 XX 万 QPS」。

## 三、测试数据准备

`docs/压测/setup.sql` 会创建：
- `LOADTEST-DISH`：下单压测专用菜品，库存 10 万（避免压到一半没库存）
- `LOADTEST-SECKILL`：秒杀压测专用商品，库存 **100**（用于防超卖断言）
- 300 条虚拟用户地址簿（id 与 user_id 相同，省掉映射）

**关键技术点**：压测用的 accessToken 由脚本用密钥**离线签发**（`lib/jwt.js`），不调用登录接口——否则：① 每次压测前要登录上千次；② 登录接口本身的限流会把压测拖垮。

验证：手工签发的用户 token / 管理 token 均能通过鉴权（HTTP 200）。

## 四、各场景结果

### 4.1 场景一：缓存读取（`/user/category/list`、`/user/dish/list`）

| 并发 | 请求数 | QPS | P50 | P95 | P99 | Max | 成功率 |
|---|---|---|---|---|---|---|---|
| 20 | 32,659 / 5 s | 6,530 | 2.7 ms | 4.6 ms | 8.9 ms | 44.9 ms | 100% |
| 200 | 193,151 / 30 s | 6,437 | 29.3 ms | 39.9 ms | 68.7 ms | 204.7 ms | 100% |
| 200（3 进程 × 100 并发） | 190,385 / 25 s | **7,608**（合计） | — | — | ~87 ms | — | 100% |

**旁证 1（DB 压力）**：30 秒 19.3 万请求期间，MySQL `Com_select` 从 443 → **444**（只涨 1 次）。
**旁证 2（GC）**：压测期间 `FGC（Full GC）= 0`，累计 GC 耗时 0.401 s（Young GC 为主），GC 不是瓶颈。

#### 缓存击穿实验（清空缓存后并发猛打）
| 步骤 | 结果 |
|---|---|
| 压前指标 | Caffeine 命中 570,183；Redis 命中 6；`missCount`（DB 回源）= 8 |
| 执行 `GET /admin/cache/clear` | category / dish 的 Redis key 全部清空 |
| 立刻 100 并发打 5 秒 | **28,433 请求**，5,709 QPS，P99 48.9 ms，成功率 100% |
| 压后指标 | Caffeine 命中 598,552（+28,369）；**`missCount` = 10（+2）** |

**结论**：2.8 万请求只回源 DB 2 次（两个 key 各一次），**回源比 14216:1**。若无击穿防护，首波并发就会打出成百次 DB 查询。

---

### 4.2 场景二：秒杀抢购 + 防超卖（`POST /user/seckill/{goodsId}`）

**参数**：200 并发、用户池 2000（每人独立 token）、库存 100、8 秒

| 指标 | 值 |
|---|---|
| 请求数 / QPS | 29,759 / 8 s → **3,725 QPS** |
| 延迟 | mean 53.6 ms、P50 48.3 ms、P90 69.4 ms、**P99 134.6 ms**、max 215.4 ms |
| 结果分布 | 抢到 **100**（0.3%）、售罄 28,259（95.0%）、重复请求 1,400（4.7%） |
| 错误率 | **0%**（无限流误伤、无 5xx） |
| **100 件库存售罄耗时** | **618 ms** |

**防超卖一致性断言（全部通过）**

| 断言项 | 期望 | 实测 |
|---|---|---|
| 成功订单数 | 恰好等于库存 100 | **100** ✅ |
| DB 库存 | 0 | **0** ✅ |
| Redis 库存 | 0 | **0** ✅ |
| Redis 已购用户集合大小 | 100 | **100** ✅ |
| 超卖数 | 0 | **0** ✅ |

补充说明：另一次 30 秒的持续压测（库存已在 warmup 阶段售罄）得到 **3,644 QPS / P99 99.7 ms / 109,356 请求 0 错误**，可作为「秒杀接口在持续压力下的吞吐」参考。两次都说明：**限量秒杀场景下，接口吞吐被"售罄判断"主导（95% 请求直接返回售罄），真正的抢购只发生在最初 618 ms 内。**

---

### 4.3 场景三：限流验证（`@RateLimit`，配置 3 次/1 秒/用户）

**方法**：故意用**同一个用户**（userId=1）20 并发高频打秒杀接口 10 秒

| 结果分类 | 次数 | 占比 |
|---|---|---|
| 被限流拦截 | **55,688** | 99.9% |
| 通过限流但重复下单（该用户已抢到） | 29 | 0.1% |
| 抢购成功 | 1 | 0.0% |
| **合计放行** | **30** | — |

**20 并发 × 10 秒 → 只放行 30 次 = 3 次/秒 × 10 秒，精确符合配置。** 同时 P99 仅 8.8 ms（被拦截的请求不进业务逻辑，开销极低）。

**对照组**：4.2 的秒杀压测用了 2000 个不同用户，**限流命中 0 次** —— 证明限流是按用户维度生效的，正常多用户抢购不会被误伤。

---

### 4.4 场景四：下单主链路（加购 + 提交订单）

**参数**：50 并发、15 秒、用户池 300（每轮 = `加购 + 提交订单` 两次 HTTP）

| 指标 | 值 |
|---|---|
| 循环数 / QPS | 3,427 / 15.2 s → **225.5 QPS** |
| 延迟 | mean **220.3 ms**、P50 **220.4 ms**、P90 254.9 ms、P95 269.2 ms、P99 300.9 ms、max 359.7 ms |
| 成功率 | **100%**（无库存不足、无异常） |
| 落库校验 | 生成订单 **4,040** 条、测试菜品库存正好减少 4,040 → **账实相符** ✅ |
| GC | 期间 `FGC = 0`，累计 GC 1.117 s |

**瓶颈定位（本报告最有价值的一段）**

延迟分布是 **P50 ≈ 均值 ≈ 220 ms，P99 仅 300 ms** —— 请求被"均匀地拖慢"，而不是少数请求抖动，这是**资源排队**的典型特征。

证据链：
1. `Max_used_connections = 10`（MySQL 全局最大连接数）＝ 应用侧 8 条 + 命令行 2 条 → **应用实际只用了 8 条 DB 连接**。
2. `application.yml` 里 **没有配置 `spring.datasource.druid.max-active`** → 用的是 Druid 默认值 **8**。
3. 一次下单要访问 DB 约 6 次（查地址、查购物车、扣库存、插订单、插明细、清购物车），50 个并发请求抢 8 条连接 → 必然排队。
4. 每请求耗时 220 ms ≈ 8 连接 × 单请求 DB 服务时间 / 并发度，与观察值吻合。

**结论：当前下单接口的吞吐上限由数据库连接池（8 条）决定，而不是 CPU/GC/Redis。**

## 五、优化建议（都可再测一次做"优化前后对比"）

| # | 优化项 | 预期 | 验证方式 |
|---|---|---|---|
| 1 | Druid `max-active`：8 → 30~50，并设置 `initial-size`/`min-idle` | 下单 QPS 显著提升、P99 下降 | 改配置后重跑同参数下单场景，对比 QPS/P99 |
| 2 | 下单接口的 6 次 DB 访问可合并（如库存扣减与插订单用一次批量；购物车查询与清空合并） | 减少连接占用时间 | 同上 |
| 3 | 秒杀接口每次请求要走 **2 次 Redis Lua**（限流 1 次 + 扣减 1 次） | 合并/本地限流可提升吞吐 | 对比改造前后 QPS |
| 4 | 压测机与应用分离（或压测器多进程/独立机器） | 才能探到应用真实容量上限 | 与本次数字对比，说明"之前测到的是压测机上限" |
| 5 | 清理 `/test/**` 接口 | 这些无鉴权接口会真实扣库存，压测/演示时极易被误用 | 代码审查 |

**亮点版（口头讲）**

## 七、如何复现

```bash
# 0. 依赖：Node 18+、MySQL/Redis/RabbitMQ、应用已启动在 8080

# 1. 准备测试数据（幂等，可重复执行）
mysql --default-character-set=utf8mb4 -uroot -p sky_take_out < docs/压测/setup.sql

# 2. 预热秒杀库存（把 <goodsId> 换成 setup.sql 输出的 loadtestGoodsId）
#    先清 key 再预热，避免 setIfAbsent 跳过
redis-cli -h <host> del seckill:stock:<goodsId> seckill:users:<goodsId> seckill:last_dispatch:<goodsId>
curl -X POST -H "token: <adminToken>" http://localhost:8080/admin/seckill/warmup/<goodsId>

# 3. 跑场景
node docs/压测/run.js read      --c=200 --d=30
node docs/压测/run.js seckill   --c=200 --d=30 --goods=<goodsId> --pool=2000
node docs/压测/run.js ratelimit --c=20  --d=10 --goods=<goodsId>
node docs/压测/run.js order     --c=50  --d=15 --dish=<dishId> --pool=300

# 4. 清理（务必执行）
mysql --default-character-set=utf8mb4 -uroot -p sky_take_out < docs/压测/cleanup.sql
```

> Windows 注意：`mysql` 命令要加 `--default-character-set=utf8mb4`，否则中文写入 varchar 会报 `Data too long`。

## 八、JMeter 等价迁移规划（同样场景用 JMeter 复跑一遍）

> 目的：JMeter 是面试官更熟悉的工具名；脚本可以证明方法论，JMeter 负责"标准工具"背书。两者结果应可互相印证。

### 8.1 环境准备
1. 下载 Apache JMeter 5.6.3（需 JDK 8+，本项目已有 JDK 17）→ 解压即用，不装服务。
2. 启动 GUI 只用于**调试**；正式压测一律用 `jmeter -n -t plan.jmx -l result.jtl -e -o report/`（非 GUI 模式，GUI 模式自身会吃掉大量性能）。

### 8.2 计划结构（对应四个场景，可放同一 plan 用「线程组 + 模块控制器」拆开）
| JMeter 元件 | 对应实现 |
|---|---|
| **Thread Group** | 线程数 = 并发；Ramp-up 建议 5~10s（避免瞬间冲击造成假 P99）；循环次数 = 勾选「无限」+ 调度器 Duration |
| **HTTP Request Defaults** | 服务器 `localhost`、端口 `8080`、`Content-Type: application/json` |
| **HTTP Header Manager** | `user_token` = `${userToken}`（从 CSV 读） |
| **CSV Data Set Config** | `users.csv`：`userId,userToken,addressBookId`。**这是关键**：秒杀/下单必须一用户一行，否则会撞"一人一单"和"3 次/秒/用户"限流。用 `docs/压测/lib/jwt.js` 批量生成 2000 行 CSV |
| **JSON Assertion / 响应断言** | 断言 `$.code == 1`；秒杀场景再断言 `$.data.code`，用 **JSR223 PostProcessor + groovy** 把 `data.code` 拆成 `biz_success / biz_soldout / biz_dup` 三个自定义指标 |
| **Constant Throughput Timer** | 若要做「固定速率」模型（与闭模型互补），用它对 Thread Group 限速 |
| **聚合报告 / Summary Report** | 看 QPS、Average、P90/P95/P99、Error% |
| **Backend Listener（InfluxDB+Grafana）** | 可选进阶：把指标实时写进 InfluxDB 出时序图，面试时更好看 |

### 8.3 各场景的线程组参数（与本次 Node 脚本对齐）
| 场景 | 线程数 | Duration | 取样器 | CSV |
|---|---|---|---|---|
| 缓存读取 | 200 | 30 s | GET `/user/category/list?type=1` + GET `/user/dish/list?categoryId=11`（轮换控制器） | 单用户即可 |
| 秒杀 | 200 | 30 s | POST `/user/seckill/${goodsId}` | 2000 行用户 |
| 限流 | 20 | 10 s | POST `/user/seckill/${goodsId}` | **只有 userId=1 一行**（故意同用户） |
| 下单 | 50 | 15 s | POST `/user/shoppingCart/add` → POST `/user/order/submit`（同一事务控制器内顺序执行） | 300 行用户 |

### 8.4 注意事项（JMeter 特有的坑）
1. **必须开 Keep-Alive**（HTTP Request 勾选 `Use KeepAlive`）并在 `jmeter.properties` 调大 `httpclient4.max_body_size`（本项目订单号较长，避免截断）。
2. JMeter 单机 GUI 模式跑的 QPS 通常低于本项目自研脚本（GUI 与请求线程抢资源），所以**对比只能在"同工具同参数"内做**，跨工具比 QPS 没有意义。
3. 断言失败会把该请求记为 Error，因此**秒杀的"售罄/重复"必须用后置处理器归类而不是断言失败**，否则错误率会显示 95%，误导结论。
4. 结果文件 `result.jtl` 建议用 `-l` 落盘后自己做分位数统计，或直接用 HTML 报告。
