## 一、项目介绍（背下来）

### 30 秒版
> "我从 0 独立做了一个**线上超市**的分布式电商平台，Spring Cloud Alibaba + Vue3，拆了 **8 个微服务**：网关、认证、用户、商品、库存、购物车、订单、支付。
> 核心是**下单主链路**：用 **Seata AT** 保证"锁库存 + 建单"的原子性，长尾用**本地消息表 + MQ** 做最终一致，**延迟插件 + XXL-JOB 扫描兜底**做超时关单。
> 另外做了**多实例定时任务协调**（XXL-JOB 分片 + `SKIP LOCKED`）、**多级缓存的多实例一致性**、以及 **AT / 显式 TCC 两种事务模式的对照实现**。"

### 2 分钟版（加架构与取舍）
在 30 秒版基础上补：
1. **工程底座**：多模块 Maven，7 个 starter 化公共模块（统一返回 / 异常 / traceId / 鉴权 / 幂等 / MQ / MyBatis），8 个服务零重复代码接入。
2. **一致性分场景**：同步短链路用 AT；长尾用本地消息表；数据同步用 MQ 最终一致；**长链路绝不用 Seata**（全局锁是中心化锁，长事务会把吞吐拖死）。
3. **安全和信任边界**：网关统一验签 + JWT 黑名单（登出即失效）+ **无条件剥离入站 `X-User-*`**（防伪造）+ 注入可信头；服务端 `@RequirePermission` 细粒度 RBAC；资源层按 `user_id` 防越权。
4. **自证**：写了跨服务的一致性核对 SQL，用 `locked_stock` / 未支付订单锁定总量 / 库存流水净额**三方交叉验证**，并做"已支付必有 confirm 流水、已取消必有 release 流水"的正反向完整性校验。

> ⚠️ **只讲这三块真的做了的**：一致性（AT/TCC/本地消息表）、多实例协调、缓存一致性、安全、并发幂等、自证核对。
> **不要讲**：灰度发布、SkyWalking/Prometheus 可观测、Redisson —— 这三项目前**代码里没有**（只有 `spring-boot-starter-actuator`，没有引 SkyWalking / micrometer，Redisson 依赖没被任何代码使用）。

### 两个项目的分工（**最值钱的定位话术**）
> "我有两个同题材项目，**故意做了分工**：
> **单体版**聚焦**单点极致** —— 秒杀（Redis+Lua 预扣）、对账、三层延时兜底；
> **微服务版**聚焦**分布式难题** —— Seata 三种模式对比、多实例协调、缓存一致性、服务边界隔离。
> **同一个技术点，两个项目讲不同维度，不重复。**"

> 面试官若问"微服务为什么不做秒杀"：
> "秒杀是**单点极致**问题，单体已覆盖；微服务我做**单体做不了的事**（多实例、分布式一致性）。"

## 三、高频追问 Q&A

### A. 事务与一致性
**Q1 下单为什么用 Seata？**
不用的话"扣库存成功但建单失败"就不一致。可选：本地消息表 / TCC / Saga / 最大努力通知。选 AT 因为**零侵入**（加注解），且同步段并发可接受。

**Q2 AT 原理？**
代理数据源；一阶段执行 SQL + 写 undo_log + 抢**全局锁** + 提交本地事务；二阶段提交则异步删 undo_log，回滚则用 undo_log 反向补偿。

**Q3 全局锁防什么？怎么证明？**
防**脏写**：AT 一阶段已提交本地事务，其他事务修改同一行后，若本事务全局回滚，undo_log 的旧镜像会**覆盖别人的更新**。加了全局锁后，其他写同一行的事务会被挡住，直到本事务二阶段结束。
> ⚠️ **这个"`@GlobalLock` 前后对比"的并发实验本项目没做** —— 原理能讲清楚，但别说"我写了实验证明"。

**Q4 AT 的隔离级别？**
默认**读未提交 + 全局锁**（因为一阶段就提交了）。跨事务的读要用 `@GlobalLock` 才安全。

**Q5 长链路为什么不用 Seata？**
全局锁是**中心化锁**，长事务会长期持有 → 吞吐崩。所以长尾用**本地消息表 + MQ 最终一致**。

**Q6 本地消息表怎么保证原子？**
业务与 `local_message` **同库同事务**写入 → 定时任务扫描补发 → 成功置状态；消费端幂等，允许"至少一次"。

**Q7 TCC 三大坑？**
- **空回滚**：Cancel 先到、Try 未执行 → `cancelBegin` 发现无 fence 记录 → **插占位 + 直接成功**；
- **悬挂**：Cancel 后 Try 才到 → `tryBegin` 发现已是"已回滚" → **拒绝执行**；
- **幂等**：fence 状态判定 + `inventory_log` 唯一键双保险。

**Q8 为什么用显式 TCC 而不是 Seata 自动 TCC？**
Spring Cloud 下要打通 `@LocalTCC` + XID 传播 + 二阶段本地回调，链路长坑多；**显式编排把补偿握在自己手里**，再配本地消息表 + XXL-JOB 保证补偿最终执行。

**Q9 AT / TCC / Saga 怎么选？**
AT：同步短链路、零侵入。TCC：高并发、需精细控制（但要做三大坑防护）。Saga：**长事务、多步骤、可补偿**，无隔离性（可能脏读），实现重。**分场景选，不一招通吃。**

**Q10 延时关单？**
延迟插件 `x-delayed-message`（`x-delay` 头，**任意延时、无队头阻塞**）；消费失败走重试队列。**为什么不用 TTL+DLX**：TTL 队列有**队头阻塞**，延时不准。

**Q11 为什么还要 XXL-JOB 扫描兜底？**
延时消息可能丢（MQ 抖动/投递失败）→ 订单永远挂着。**扫描 `status=0 and expire_time<now`** 是最后一道保险。**双保险**。

### B. 缓存
**Q12 多级缓存怎么做的？**
Caffeine(L1 进程内) → Redis(L2) → DB；回源逐层回填。商品详情已落地（`SpuService.detail`）。
> ⚠️ **加缓存前后的 QPS/p99 对比还没跑** —— 见 [08](08-audit-findings.md) §4.2 待压测清单。

**Q13 多实例 Caffeine 怎么一致？**
更新时"删本地 + 删 Redis + **Pub/Sub 广播**"→ 所有实例删自己的 L1。

**Q14 Pub/Sub 丢消息怎么办？（**核心**）**
Pub/Sub 是"通知"语义，不持久化、无 ACK。**换成"查状态"**：
- 写时除了删缓存，还往 Redis 的**失效日志**里追加一条：`ZADD cache:inval:{app} score=全局序号 member=fullKey`（序号由 `INCR` 得到），并裁剪只留最近 1000 条；
- 每个实例**每秒轮询**全局序号，落后就按序号区间 `ZRANGEBYSCORE (seen, remote]` **精确取出漏掉的 key 逐个失效** → 最坏陈旧窗口 = 轮询间隔；
- **兜底**：取日志里最老一条的 score 作为"可重放下界"，若 `seen < 下界`（说明日志被裁剪、无法重放）→ **回退全量失效**，保证**永不脏读**；
- 再加 **epoch 检测**覆盖 Redis 重启（版本号丢失时只能全清）+ **TTL** 终极兜底。

> 为什么不用"全局版本号 + 全清"的简单版？因为**任意一个 key 失效都会清空所有实例的整个 L1**，L1 实际就废了，写入一多就是回源 DB 洪峰。**精确重放 + 截断水位兜底**才能兼顾"命中率"和"不脏读"。
> 细节：`seenVersion` **只由轮询推进**（Push 不推进）——否则"丢旧通知、收新通知"会掩盖丢失。

**Q15 为什么删缓存不更新缓存？**
更新缓存要写两处 + 有**并发写顺序**问题；删除最简单安全，且**本地缓存"只删不写"→ 天然免疫广播乱序/重复**。

**Q16 穿透/击穿/雪崩？**
穿透：空值缓存 / 布隆过滤器；击穿：分布式锁重建（或逻辑过期）；雪崩：**随机 TTL** + 多级缓存。

**Q17 哪些数据不该进 L1？**
**库存、余额、券**这类强一致数据——判据"旧 1 秒会不会出事故"。库存靠 **DB 条件更新**。

### C. 并发与幂等
**Q18 防超卖？为什么不用 `for update`？**
`update ... where available_stock >= n`，影响行数 0 即失败。**不用 `select ... for update`**：排他锁要持有到事务结束，易阻塞/死锁，而且高并发下锁竞争严重。
> ⚠️ **"200 并发抢 10 → 成功恰为 10"这个实验还没跑**（脚本已备好，见 [08](08-audit-findings.md) §4.2）—— 跑出来之前别在简历里写这个数字。

**Q19 幂等怎么做？**
- 下单：网关 token 预检 + 服务端 `@Idempotent`（Lua `GET+DEL` 原子消费）+ `order_no` 唯一索引；
- 支付回调：`payment_no` 唯一 + status CAS + 至少一次投递；
- MQ 消费：Redis 去重（失败要 **release**）+ 业务 CAS。

**Q20 库存归还为什么必须幂等？**
**重复归还会让库存虚增**（比超卖更隐蔽）。靠 `inventory_log` 唯一键 `(order_no, type, sku_id)`。

### D. 多实例 / 调度
**Q21 `@Scheduled` 多实例的问题？**
每个实例都跑 → **重复执行**。解决：分布式锁（串行、浪费机器）/ 数据库状态抢占 / **XXL-JOB 分片广播**（既不重复又并行）。

**Q22 分片 + SKIP LOCKED 为什么都要？**
分片是"按数据划分"，实例掉线那片就没人处理 → 需**僵死回收 + CAS 幂等**兜底；`SKIP LOCKED` 解决**多实例抢同一批行时相互阻塞**——跳过被锁行，各领各的。

**Q23 为什么"抢占"和"投递"分两个事务？**
`FOR UPDATE` 的锁在提交前一直持有；若把"发 MQ"放事务里，**持锁时间 = 网络耗时**。所以：**短事务抢锁（只改状态）→ 提交 → 事务外投递**。**锁要短。**

### E. 架构与安全
**Q24 为什么一服务一库？跨服务怎么拿数据？**
边界清晰、独立扩缩容、事务边界清楚；跨服务**绝不 join**——实时查走 Feign，允许延迟走 MQ 同步或**快照冗余**。

**Q25 网关怎么鉴权？内部怎么信任用户身份？**
网关验签 JWT + 查黑名单；通过后**先剥离所有入站 `X-User-*`**（防伪造），再注入可信头。内部服务只信任这些头，前提是"外部流量必经网关"。

**Q26 越权怎么防？**
网关只做粗粒度；**服务层按 `user_id` 过滤资源**（地址、订单、支付越权都校验归属）。

**Q27 动态菜单怎么实现？刷新丢路由怎么办？**
菜单树来自 `sys_permission`（`component` 字段即前端组件路径）→ `router.addRoute` 动态注入；守卫用 `loaded` 标志重建；**404 兜底必须最后加**。

**Q28 traceId 怎么贯穿？**
网关生成 → MDC + 响应头 → Feign 拦截器透传 → 下游读头写 MDC；MQ 消息体携带。**排障时一个 ID 串起全链路。**

**Q29 如果让你做灰度发布，你会怎么做？**（**设计题，不是已实现** —— 本项目没做，别答成"我做了"）
Nacos 权重只能做"比例"，**无法按请求特征定向**。要按 header / 用户哈希定向，就自己实现 `ReactorServiceInstanceLoadBalancer`：从 `RequestDataContext` 取 header 匹配实例的 `metadata.version`；**目标版本无实例时必须回退全量**，否则会把流量打到空。灰度实例用 Nacos metadata 打标（如 `version: v2`）。
> 更轻量的替代：网关上按用户哈希改写路由到带版本前缀的服务名。

**Q30 降级为什么"读 fail-safe、写 fail-closed"？**
读接口降级返回兜底数据即可；**写接口必须返回失败**让上游回滚/重试——**绝不能降级成"成功"**（否则超卖/账不平）。
> 本项目实践：`ProductClientFallbackFactory`（读）返回 `11002` 让上游决定；`InventoryTccClientFallbackFactory`（写）**fail-closed 返回失败**，让编排走补偿。

### F. 工程与排障
**Q31 线上变慢你会怎么查？**（**通用方法论，本项目未接可观测链路**）
链路（分布式追踪找慢调用）→ 指标（QPS / RT / 错误率）→ 资源（**连接池 `pending > 0` = 池子不够；`usage_seconds_max` 大 = 长事务 / 慢 SQL**）→ GC / CPU。
> 本项目目前**只有 `spring-boot-starter-actuator`**，没有引 SkyWalking / micrometer。实战里我用的是"日志打点 + Arthas + 直接查 DB/队列状态"这套土办法（见 [08](08-audit-findings.md) §6 排查方法备忘）。

**Q32 你踩过哪些坑？**（真实经历，最加分）

**框架 / 工程类**
① 忘建 `AutoConfiguration.imports` → **自动装配整个失效**，异常走默认错误页；
② Spring 6.1 参数校验抛 **`HandlerMethodValidationException`**（不是 `ConstraintViolationException`），不处理就掉进兜底；
③ Seata 容器注册的是**容器 IP**，宿主服务连不上 → 用 `SEATA_IP` 指定；
④ `@Transactional` **同类自调用失效** → 抢占逻辑拆成独立 Bean；
⑤ 自定义 parent POM（没继承 `spring-boot-starter-parent`）**漏了 `-parameters`** 编译参数。Spring 6.1 已移除 `LocalVariableTableParameterNameDiscoverer`，导致**所有未显式命名的 `@RequestParam`/`@PathVariable` 全部抛 `IllegalArgumentException`**，被全局兜底成"系统繁忙"。**14 个接口同时挂**，而且报错完全看不出原因 —— 最后是单独起一个实例把日志打到文件才抓到堆栈。**教训：显式写 `@RequestParam("name")`，或确保编译器带 `-parameters`。**

**消息 / 数据类**
⑥ **MQ 消息被"二次编码"** → 整条异步链路静默失效：生产者把已经 `toJson` 过的字符串交给 `Jackson2JsonMessageConverter`，转换器又序列化一遍，body 变成 `"{\"...\"}"`，消费端必然反序列化失败。**现象是"支付成功但订单永不推进"**，靠"查队列深度 → 读死信消息头"才定位。
⑦ `BeanUtils.copyProperties(source, target)` **参数写反**（传了空 DTO 当 source）→ 接口静默返回空对象，下游拿不到 `userId` → 越权校验失败把下单整条链路打死。**这种"不报错但数据是空的"最阴。**
⑧ InnoDB 的**唯一键冲突只回滚那一条语句**（语句级回滚）→ 所以"先 `update` 再 `insert`、catch 唯一键异常放行"是**错的**：事务里已成功的 `update` 会照常提交 → **重复扣减**。正确做法是**把唯一键闸门放在库存变更之前**（先 insert，成功才 update）。

**环境类**
⑨ JDK 17 的 `file.encoding` **跟随平台区域设置**（中文 Windows = GBK），用 `java -jar` 启动时读 Nacos 拉下来的 UTF-8 YAML 会抛 `MalformedInputException`；IDE 里能跑是因为 IDE 设了 UTF-8。**部署脚本/镜像必须显式 `-Dfile.encoding=UTF-8`。**

## 五、简历（结果导向版，可直接粘贴）

> **shop_Cloud · 线上超市微服务电商平台** ｜ 个人项目 ｜ 2025.xx – 2026.xx
> **技术栈**：Spring Cloud Alibaba（Nacos / Gateway / Sentinel）· Seata(AT/TCC) · RabbitMQ · Redis · MySQL · XXL-JOB · Vue3
>
> 从 0 独立设计并实现 8 个微服务的电商平台（一服务一库、服务间不 join），沉淀 7 个 starter 化公共模块（统一返回 / 异常 / traceId / 鉴权 / 幂等 / MQ / MyBatis）与约 190 个 Java 文件；前端用 pnpm workspace 实现管理端与商城端双应用复用。

- **给"锁库存 + 建单"做了 AT 与显式 TCC 两套对照实现，并用状态机收敛 TCC 的四个经典陷阱。** AT 用 `@GlobalTransactional` 覆盖同步短链路；另手写显式 TCC（自管 `xid`/`branchId`），以 `tcc_fence` 状态机（TRYING→COMMITTED→CONFIRMED / ROLLBACKED）逐一解决**空回滚、悬挂、幂等、确认-回滚互斥**，并通过配置开关切换两种模式。实测：`try→confirm`（状态 `1→3`）、`try→cancel`（`1→2`）与库存变动严格一致。

- **定位并修复了一个让整条异步链路"静默失效"的消息缺陷。** 现象为"支付成功但订单永不推进"。按 `应用日志 → 订单状态 → MQ 队列深度 → 死信消息头` 逐层排查，定位到消息转换器对**已序列化的 JSON 字符串二次编码**，导致消费端必然反序列化失败、重试 3 次后沉入死信。修复后事件恢复投递，并补齐**本地消息表 + 手动 ack + 有限重试 + 死信**，投递语义从"至多一次"提升到"至少一次"。

- **把幂等闸门从"查"改成"写"，消除竞态窗口。** 将库存流水唯一键 `(order_no, type, sku_id)` 前置为闸门——**先写流水、成功才变更库存**；配套多 SKU 按 `skuId` 排序加锁避免死锁、释放场景空回滚不抛异常避免重试风暴。并用跨服务一致性 SQL 自证：`locked_stock` = 未支付订单锁定总量 = 流水净额，**三方零差异**。

- **多实例定时任务协调 + 超时关单双保险。** XXL-JOB 分片广播并行，`SELECT ... FOR UPDATE SKIP LOCKED` 在短事务内原子抢占（投递移至事务外，避免网络耗时持锁），叠加僵死回收与 CAS 幂等；超时关单采用"延迟交换机 + 扫描兜底"，实测在延迟链路故障时扫描仍能关闭订单并**完整归还库存**。

- **多级缓存一致性：用"可验证的拉取"兜住"不可靠的推送"。** Caffeine + Redis 两级缓存，将 Pub/Sub 降级为加速手段，改用带序号的**失效日志 + 轮询精确重放**，日志被裁剪时回退全量失效以保证不脏读；叠加 epoch 检测覆盖 Redis 重启、TTL 终极兜底，最坏陈旧窗口收敛到轮询间隔。

- **安全与可观测底座。** 网关统一验签 + JWT 黑名单（登出即失效）+ **无条件剥离入站 `X-User-*` 防伪造**，服务端 `@RequirePermission` 做细粒度 RBAC，资源层按 `user_id` 防越权；全链路 traceId 经 网关 → MDC → Feign → MQ 贯通。
