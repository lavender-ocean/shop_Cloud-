### 3.1 🔍 为什么 p50 高达 663ms？

200 个请求总耗时 822ms → **822 ÷ 200 ≈ 4.1ms/次**，说明请求被**完全串行化**。

串行化来源是**数据库行锁**：200 个请求打同一个 `sku_id`，最终都执行同一条
`UPDATE inventory ... WHERE sku_id = 900001`，InnoDB 行级排他锁让它们必须排队。

**这恰恰解释了"为什么不会超卖"** —— 三重保障叠加：
1. `WHERE available_stock >= 1` 条件更新（影响行数 0 即拒绝）
2. **同一行的行锁把并发串行化**（不会有两个事务同时读到相同余量）
3. 应用层 `insert-first` 幂等闸门（先写唯一键流水，成功才改库存）

> 这条也**修正了 T5 的方法**：T5 改用 **50 个不同 SKU**，避免行锁串行化，才能测出真实并发能力（见 §5）。

### T6 多实例分片（并行且不重复）✅

**做法**：临时起**第二个 order 实例**（`--server.port=18086 --xxl.job.executor.port=9998`），XXL-JOB 的 `localMessageCompensateHandler` 路由策略是 **`SHARDING_BROADCAST`** → 两个执行器自动分到 `0/2` 与 `1/2`。

**验证结果**：

| 步骤 | 结果 |
|---|---|
| 造数据 | 100 条 `local_message`（`status=0`，`msg_id=T6-001..100`）|
| **按分片预分布** | `MOD(id,2)=0` → **50 条**；`MOD(id,2)=1` → **50 条**（刚好均分）|
| 两个实例各自执行 | `192.168.150.1:9999` → **分片 1/2**、`192.168.150.1:9998` → **分片 0/2**，`handleCode=200` |
| **终态** | 100 条**全部** `status=1`（已投递）；`未投递=0` / `投递中=0` / `待重试=0` |
| **消费端去重** | Redis 中 `idempotent:consume:order-created:T6-*` 共 **100 个键** → **每条消息只被消费一次** |
| 清理 | 残留 0 |

**为什么"不重复"是结构性保证**：
1. 分片键 `MOD(id, shardTotal) = shardIndex` → **每行只属于一个分片**，两个实例的查询集合天然不相交；
2. `SELECT ... FOR UPDATE SKIP LOCKED` → 即使两实例抢到同一批，也会**跳过已被锁定的行**而不是阻塞等待；
3. 抢占后立刻 `markClaimed`（`status=0 → 2`）在**短事务**内提交，投递放在事务外（避免网络耗时持锁）；
4. 兜底：`releaseStaleClaims` 回收"抢占超过 60s 未完成"的僵死行（`status=2 → 3, next_retry_time=NOW()`）。

**综合**：**两个实例并行处理 100 条，合计 == 100、无重复、无遗漏、无僵死** ✅

## 7. 踩坑与发现（**本轮最有价值的部分**）

### ① 🔴 网关路由级限流 3 QPS —— 让第一次压测"看起来像故障"

**现象**：经网关压 `/api/product/spu/page`，30s 只有 **90 次成功**，其余 **236,369 次 HTTP 429**。两轮（50/100 并发）都恰好 90 次。

**定位**：90 = 30s × **3 QPS** → 去 Nacos 的 `SENTINEL_GROUP` 查规则，找到：

| 配置 | 资源 | 阈值 |
|---|---|---|
| `shop-gateway-gw-flow-rules.json` | 路由 **`shop-product`** | **3 QPS** |
| `shop-order-flow-rules.json` | `order:create` | **3 QPS** |
| `shop-product-flow-rules.json` | `product:getSku` | 5 QPS |

**处理**：**不改配置**，改用**直连服务端口**（绕过网关）测真实性能；同时保留"经网关"这一轮作为**限流生效的证据**。

**⚠️ 对 T3 的影响**：`order:create` 限流 **3 QPS**，所以经网关压下单最多 90 单/30s。要测下单真实吞吐，需要**临时放宽该规则**（或同样直连 + 自行准备幂等 token）。

### ② 🔴 机器上有**两台 Redis**，服务连的是宿主机原生那台

**现象**：`docker exec shop-redis redis-cli dbsize` → **0**，`keyspace_hits/misses` → **0/0**；但幂等 token、加购、SPU 详情**全部正常**。

**定位**：
```
netstat:  0.0.0.0:6379   → PID 14880（Docker 端口代理 → shop-redis 容器）
          127.0.0.1:6379 → PID 27232（宿主机原生 Redis，无密码）
连宿主机那台: DBSIZE=232，全是本项目的 key
  cache:shop-product:spu:detail:…  cache:inval:shop-product  cache:ver:shop-product
  cart:… idempotent:token:… auth:refresh:… auth:perms:… cache:epoch:shop-*
  累计 keyspace_hits=696,269 / misses=839,103（命中率 45.4%）
```

**根因**：Nacos `common-dev.yaml` 里 **`spring.data.redis.*` 配置被注释掉了** → 服务走 Spring Boot 默认 `localhost:6379` → 命中了**宿主机原生的 Redis**，而不是 compose 里配了 `<见 infra/.env>` 密码 + AOF 的那台。

**影响（要记住）**：
1. `infra/docker-compose.yml` 的 redis（密码 `<见 infra/.env>`、AOF 持久化）**实际未生效** —— 换台没装原生 Redis 的机器部署时行为会变
2. **AOF 持久化没生效** → Redis 一重启数据全丢（本轮就发生过：原生 Redis uptime 只有 26 分钟）
3. 之前"Redis 命中率 = 0"的读数**是测错了实例**，已在本报告中更正

**建议**：在 Nacos 里显式配 `spring.data.redis`（host/port/password/database），或者**停掉宿主机原生 Redis** 让服务连 compose 那台。

### ③ T1 的 100 并发比 50 并发 **更慢**
QPS 3,105 → 2,786，p99 39ms → 91ms。**同机压测下 50 并发已接近饱和**，继续加压只是排队。这条对"容量规划"的直觉很有价值。

### ④ 压测脚本用 `fetch` 压不出真并发
Node 的 `fetch`/undici 默认连接池会限制并发度。改用 `node:http` + `maxSockets` 后，200 个请求才是真并发（否则 T4 的争抢场景失真）。

### ⑤ 🔴 T3 首次全挂：JS 数字精度把雪花 ID 截断了（**我自己的测试脚本 bug**）

**现象**：T3 冒烟时 3,988 次请求全部失败，`13002 ADDRESS_NOT_FOUND` × 3,581、`11001 RATE_LIMIT` × 407 —— **一单没建出来**。但单独用 curl 打一次下单却成功。

**定位**：`13002` 是"地址不存在"。地址明明有效，于是怀疑传参。一算就明白了——

```
scenario JSON 里写的: "addressId": 2109660387913506818
Node JSON.parse 之后:  2109660387913506800   ← 末位被抹平了！
```

**雪花 ID 超过 `2^53`，写成 JSON 数字字面量会被 JS Number 精度截断。** 同理 `skuId: 2107390427584630786` 也会变成 `…630800`。

> 为什么之前 T1/T2/T5 没踩到：那些 ID 走的是 **URL 字符串**；T4 用的 `900001` 是个小数字。

**修复**：**大 ID 一律写成字符串** —— `"addressId": "2109660387913506818"`。Jackson 能把 `"123"` 强制转成 `Long`，所以后端不用改。
修复后 T3 冒烟 **705/705 全成功**，且**净增订单数 705 == 成功数 705**。

### ⑥ 🔴 清理脚本第一次写错了：`locked_stock` 是计数列，删流水不会让它变小

**现象**：T3 跑完执行清理，`order_info` 里的 `LOADTEST` 订单已全删，但 `inventory.locked_stock` 仍是 **8,483**（= 717 冒烟 + 7,766 本次），`available_stock` 少了一大截 → **假性缺货**。

**根因**：清理脚本只 `DELETE` 了 `inventory_log`，但 `locked_stock` 是 `inventory` 表上的**独立计数列**，不会随流水删除而变化。

**修复**（`bench/data/cleanup-orders.sql`）：**先算再删再还**——
```sql
SET @rel = (SELECT COALESCE(SUM(quantity),0) FROM inventory_log
            WHERE sku_id=@sku AND type=2
              AND order_no IN (SELECT order_no FROM order_info WHERE remark='LOADTEST'));
-- ...删流水、删订单...
UPDATE inventory SET locked_stock = GREATEST(locked_stock - @rel, 0),
                     available_stock = available_stock + @rel
WHERE sku_id = @sku;
```

> **教训**：清理"带计数列的库存"时，光删明细不够，必须同时**归还计数**。否则下次压测的基线就是错的。
